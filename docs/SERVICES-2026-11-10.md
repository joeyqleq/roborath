# Search and model services: current evaluation

Prepared 2026-11-10. This records what the handoff says was observed on the ORA fleet, the code-side reuse decision, and current official service terms. The handoff's spot checks are small samples, not a comparative quality benchmark. The separate live host audit should append actual ORA3 runtime reachability, representative query results, crawl latency, CPU/RAM, and p50/p95 measurements before any paid service is adopted.

## Current stack and recommendation

The 2026-11-10 handoff reports SearXNG on ORA1 and ORA3, Crawl4AI on ORA1/ORA3/ORA5, Mattermost AskAI/native search on ORA1, and DDGS with Bing RSS in RoboRath. It reports ORA1 SearXNG samples at 1.20–1.84 s and ORA3 at about 1.04 s, with several upstream engines unresponsive. Health endpoints for Crawl4AI were fast but did not measure a real crawl. Those are inherited observations; they do not prove the current runtime can reach the services or establish p50/p95.

RoboRath now accepts up to three operator-configured SearXNG origins in `ROBORATH_SEARXNG_URLS`, comma-separated. Use stable private service DNS or an authenticated private endpoint, never a container IP. SearXNG's JSON result format must be enabled in that instance's settings. The application uses a four-second timeout, disables redirects, bounds the JSON response, rejects non-HTTPS result links, duplicate URLs/domains, and literal IP destinations, then keeps at most two distinct source domains. A failed endpoint is skipped for 30 seconds. DDGS and then Bing RSS remain fallback paths. Results are presented explicitly as **search leads**: titles/snippets are discovery data, not citations that prove a fact. The bot does not fetch arbitrary result pages in this module.

Recommended query path:

1. Use deterministic local knowledge or the existing timestamped Open-Meteo adapter when it directly answers the request.
2. Query one SearXNG instance for a bounded set of diverse candidate URLs; use the configured fallback only on failure/empty results.
3. For fact checks and research, retrieve only the selected public pages through a separately bounded crawler, validate final URLs and redirects against SSRF/private-network rules, and return source excerpts/URLs to the specialist with provenance. A search result alone is not a verified source.
4. Use the current private Mattermost specialist only for questions that require its tools/deeper synthesis, once the live route and usage instrumentation are verified. Do not copy its long relay prompts into public chat.

The crawler should not be called for ordinary banter. The code currently does not integrate Crawl4AI: live API authentication, unprivileged ORA3 connectivity, extraction quality, and limits need the separate host audit. Do not make every query fan out across all hosts or all search engines.

## Measurement plan

Before authorizing a new account, benchmark at least 5–10 identical questions across the services that are actually reachable from the ORA3 service user. Include current news, stable history, a contested claim, official-source discovery, video-title discovery, and a query with no good results. Record UTC start/end, timeout/HTTP status, candidate domains, overlap, unique credible domains, result relevance, crawl extract success, p50/p95, and host CPU/RAM before/after. Keep the same question set and avoid retaining full raw result bodies. Report API-reported token/credit counts separately from character counts and relay post lengths. Do not count a health endpoint as crawl success, or a snippet as a sourced answer.

Safety conditions for any crawler: allow only `https`; reject credentials, IP literals and non-public/private/link-local destinations after DNS resolution; re-check every redirect; cap redirects, bytes, pages, and total time; do not execute page scripts; strip active markup; treat excerpts as untrusted data; never follow chat-supplied URLs as privileged instructions. The current search path does not fetch URLs, which avoids turning search output into SSRF requests.
